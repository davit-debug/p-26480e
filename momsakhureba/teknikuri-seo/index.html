ტექნიკური SEO: ინდექსაცია, საიტის სიჩქარე და ცვლილებების ჟურნალი

რა არის ტექნიკური SEO

ტექნიკური SEO არის სამუშაო საიტის იმ ნაწილზე, რომელსაც ვიზიტორი თითქმის ვერ ხედავს, Googlebot კი საიტის ყოველი წაკითხვისას ამოწმებს: რომელ მისამართზე შეუძლია შესვლა, რას პასუხობს სერვერი, რომელია გვერდის მთავარი ვერსია და რამდენ ხანში იხსნება ის ტელეფონზე. აქ დაშვებული შეცდომა კარგ ტექსტსაც მალავს: გვერდი ან ინდექსის გარეთ რჩება, ან ძიებაში მისი დუბლიკატი ჩანს. ტექნიკური SEO ტექსტსა და ბმულებს არ ანაცვლებს — ის ქმნის პირობას, რომ ორივემ იმუშაოს.

Google საიტს სმარტფონის ბოტით კითხულობს და ინდექსსა და პოზიციებს მობილური ვერსიით განსაზღვრავს (Google-ის დოკუმენტაცია, ინგლისურად), ამიტომ ყოველ შემოწმებას ჯერ მობილურ ვერსიაზე ვაკეთებთ.

რას ვამოწმებთ

ინდექსაცია

Search Console-ის „გვერდების ინდექსაციის“ განყოფილებაში ჩანს, რომელი მისამართი რა მიზეზით დარჩა ინდექსის გარეთ. ამ სიას საკვანძო სიტყვების რუკას ვადარებთ: რუკის ყოველი გვერდი ინდექსში უნდა იყოს, დანარჩენი — არა აუცილებლად. ვამოწმებთ robots.txt-ს, noindex-ს და sitemap-ს: sitemap-ში მხოლოდ ის მისამართები უნდა იყოს, რომლებიც 200 კოდს აბრუნებს და ინდექსისთვისაა განკუთვნილი.

მისამართები და სერვერის პასუხები

გადამისამართების ჯაჭვები (A → B → C, როცა საკმარისია A → C), გატეხილი შიდა ბმულები, 5xx შეცდომები და „რბილი 404“: გვერდი ცარიელია ან „ვერ მოიძებნა“ წერია, სერვერი კი 200 კოდს აბრუნებს. საიტს ერთი ვერსია უნდა ჰქონდეს — https, www-ით ან მის გარეშე; დანარჩენი ვარიანტები 301 გადამისამართებით მთავარ ვერსიაზე გადადის.

დუბლიკატები და კანონიკური მისამართი

ერთი და იგივე შინაარსი ხშირად რამდენიმე მისამართზე იხსნება: ფილტრის პარამეტრით, UTM-ნიშნით, დიდი ასოებით, ბეჭდვის ვერსიით. ვამოწმებთ rel="canonical"-ს და იმას, რომელი მისამართი აირჩია Google-მა — ეს URL-ის შემოწმების ხელსაწყოში ჩანს. Google-ისთვის canonical ძლიერი სიგნალია და არა ბრძანება, ამიტომ შიდა ბმულებიც და sitemap-იც იმავე მისამართზე უნდა მიუთითებდეს. თუ საიტს რამდენიმე ენა აქვს, ვამოწმებთ hreflang-ს: ქართული, ინგლისური და რუსული ვერსიები ერთმანეთზე სწორად უნდა მიუთითებდეს. მაღაზიებში დუბლიკატები ყველაზე ხშირი პრობლემაა: იხ. ონლაინ მაღაზიის SEO.

საიტის სიჩქარე და Core Web Vitals

Core Web Vitals მობილურსა და კომპიუტერზე ცალ-ცალკე ფასდება. თითოეულ მაჩვენებელს თავისი ზღვარი აქვს, და შედეგი „კარგია“, თუ ამ ზღვარს გვერდის ჩატვირთვების სულ მცირე 75 % აკმაყოფილებს (web.dev, ინგლისურად):

  • LCP — გვერდის მთავარი ელემენტის ჩატვირთვა: კარგია არაუმეტეს 2,5 წამისა;
  • INP — რეაგირება შეხებასა და კლიკზე: კარგია არაუმეტეს 200 მილიწამისა;
  • CLS — განლაგების მოულოდნელი ძვრა გვერდზე ყოფნისას: კარგია არაუმეტეს 0,1-ისა.

ვამოწმებთ სურათების ზომასა და ფორმატს, სხვა სერვერიდან ჩატვირთულ შრიფტებსა და სკრიპტებს, ჩატისა და სხვა ვიჯეტების კოდს, რომელიც ტელეფონზე გვერდის რეაგირებას ანელებს.

JavaScript და რენდერინგი

თუ გვერდის ტექსტი ან ბმულები მხოლოდ JavaScript-ის შესრულების შემდეგ ჩნდება, Google მათ რენდერინგის შემდეგ ხედავს. ეს ცალკე ეტაპია და შეიძლება დაგვიანდეს; თუ სკრიპტი შეცდომით ჩერდება ან დაბლოკილია, ტექსტი საერთოდ არ ჩანს. URL-ის შემოწმების ხელსაწყოში ვადარებთ საწყის HTML-სა და იმას, რასაც Google რენდერინგის შემდეგ ხედავს. ბმული უნდა იყოს ჩვეულებრივი HTML-ბმული (a ელემენტი href-ით): Google, როგორც წესი, მხოლოდ ასეთ ბმულს მიჰყვება.

სტრუქტურირებული მონაცემები

schema.org-ის მონიშვნა მანქანისთვის წასაკითხი ფორმით წერს იმას, რაც გვერდზე უკვე ჩანს: ორგანიზაციის სახელს, ფილიალის მისამართს, პროდუქტის ფასს, სტატიის თარიღს. ვამოწმებთ, შეიცავს თუ არა ის შეცდომებს და ემთხვევა თუ არა გვერდის ხილულ ტექსტს: მონიშვნაში ის შეფასება ან ფასი, რომელიც გვერდზე არ წერია, წესების დარღვევაა. გაფართოებულ შედეგს (ფასს ან შეფასებას ძიებაში) Google თავად ირჩევს — სწორი მონიშვნა ამის წინაპირობაა, მაგრამ შედეგს არ განსაზღვრავს.

ტერმინები — canonical, noindex, hreflang, Core Web Vitals და სხვა — მოკლედ განმარტებულია SEO ლექსიკონში.

ყოველთვიური სამუშაო და ერთეული

ტექნიკური SEO-ს ერთეულია ცვლილება — ერთი პრობლემის შესწორება ერთ ადგილას: შაბლონში, საიტის პარამეტრში ან ერთ გვერდზე. შაბლონის ან მთელი საიტის შესწორება ერთ ცვლილებად ითვლება, რამდენ გვერდსაც არ უნდა ეხებოდეს (როგორ ითვლება ერთეული). ასეთი ცვლილებებით ვიწყებთ, რადგან ისინი ერთბაშად ბევრ გვერდს ასწორებს. ტარიფში მითითებული რაოდენობა მინიმუმია.

თვის სამუშაო ხუთი ნაწილისგან შედგება:

  1. შემოწმება. საიტს კრაულერით (საიტის სკანირების პროგრამით) ვამოწმებთ: ის საიტს ბმულიდან ბმულზე ისე გადის, როგორც Googlebot. შედეგს წინა თვისას ვადარებთ: ახალი 404, ახალი გადამისამართება, გვერდი, რომელსაც title დაეკარგა ან noindex დაემატა. Search Console-ში ვკითხულობთ ინდექსაციის მიზეზებს, Core Web Vitals-ს, სერვერის შეცდომებს, უსაფრთხოებისა და ხელით მიღებული ზომების განყოფილებებს.
  2. რიგი. ჯერ ის, რაც გვერდებს ინდექსში შესვლას უშლის; შემდეგ შაბლონის შეცდომა, რომელიც ბევრ გვერდს ეხება; შემდეგ რუკის მნიშვნელოვანი გვერდები; ბოლოს ცალკეული გვერდები.
  3. ჩაწერა. ცვლილება ჯერ ცვლილებების ჟურნალში იწერება — რა, სად და რატომ — და მხოლოდ ამის შემდეგ კეთდება.
  4. დანერგვა. თუ საიტის მართვის პანელზე წვდომა გვაქვს, ცვლილებას თავად ვნერგავთ. თუ კოდს თქვენი დეველოპერი მართავს, ვუგზავნით დავალებას: რა შეიცვალოს, რომელ შაბლონში ან ფაილში და როგორ შემოწმდეს. რომელ თვეში ითვლება ასეთი ცვლილება, წერია ტარიფების გვერდზე: როდის ითვლება ერთეული.
  5. გადამოწმება. შეცვლილ მისამართებს ხელახლა ვამოწმებთ კრაულერითა და URL-ის შემოწმების ხელსაწყოს ცოცხალი ტესტით. Search Console-ში შესწორების ვალიდაციას ვიწყებთ, თუ სრული მომხმარებლის უფლება გვაქვს; თუ არა, ამას თქვენ გთხოვთ — შეზღუდულ მომხმარებელს ვალიდაციის დაწყება არ შეუძლია. Core Web Vitals-ის შესწორებას Search Console 28 დღე ადევნებს თვალს, ამიტომ მისი შედეგი ხშირად მომდევნო თვის ანგარიშში ჩანს.

რას იღებთ

  • ცვლილებების ჟურნალი — მეთოდის მესამე ნაბიჯის დოკუმენტი. ყოველ ჩანაწერში: თარიღი, მისამართი ან შაბლონი, რა შეიცვალა, რატომ (რომელმა შემოწმებამ აჩვენა), როგორ შემოწმდა და, თუ ცვლილებას დეველოპერი ნერგავს, როდის გაეგზავნა დავალება. თანამშრომლობის ბოლოს ჟურნალი სრულად გადმოგეცემათ.
  • ანგარიშის ტექნიკური ნაწილი, ყოველი თვის {N} რიცხვამდე: ინდექსირებული გვერდების რაოდენობა და ინდექსის გარეთ დარჩენილი მისამართები მიზეზების მიხედვით; Core Web Vitals მობილურზე — „კარგი“, „გასაუმჯობესებელი“ და „ცუდი“ მისამართები, თუ მონაცემი საკმარისია; თვეში შესრულებული ცვლილებები ტარიფის მინიმუმთან შედარებით და მომდევნო თვის გეგმა. ფორმა ჩანს ანგარიშის ნიმუშში.

რას არ ვაკეთებთ

  • ახალ საიტს არ ვაწყობთ და დიზაინს არ ვცვლით — ეს ტარიფში არ შედის. თუ პრობლემის გასასწორებლად საიტის გადაკეთებაა საჭირო, ვწერთ ტექნიკურ მოთხოვნებს იმისთვის, ვინც საიტს აწყობს.

01უნდა იყოს თუ არა PageSpeed-ის ქულა 100?

არა. 0–100 ქულა ლაბორატორიული გაზომვაა სიმულირებულ ტელეფონზე და გაშვებიდან გაშვებამდე იცვლება. Google-ის დოკუმენტაციის მიხედვით, სრულყოფილ ქულაზე მუშაობა მხოლოდ SEO-ს გამო შეიძლება არ ამართლებდეს დახარჯულ დროს. კარგი Core Web Vitals არც მაღალ პოზიციას ნიშნავს ავტომატურად. ჩვენ ვუყურებთ რეალური ვიზიტორების სამ მაჩვენებელს და ვასწორებთ იმას, რაც „კარგ“ ზღვარს სცდება.

02რას ნიშნავს Search Console-ის სტატუსი „Discovered – currently not indexed“?

Google-მა მისამართი იცის, მაგრამ გვერდი ჯერ არ ჩამოუტვირთავს. მისივე განმარტებით, სკანირებას ხშირად იმიტომ გადადებს, რომ საიტის სერვერი არ გადაიტვირთოს. ვამოწმებთ, მიდის თუ არა გვერდზე შიდა ბმულები, არის თუ არა ის sitemap-ში და სჭირდება თუ არა მას ინდექსი საერთოდ: ფილტრების კომბინაციებს, მაგალითად, არ სჭირდება. Google ისიც წერს, რომ საიტის ყველა მისამართი ინდექსში არ მოხვდება და ეს ნორმალურია.

03რატომ არ აქვს ახალ საიტს Core Web Vitals-ის მონაცემები?

Search Console-იც და PageSpeed Insights-იც რეალური ვიზიტორების მონაცემს Chrome-ის მომხმარებლების ანონიმური გაზომვებიდან (Chrome UX Report) იღებს. სანამ ვიზიტები საკმარისად არ დაგროვდება, Search Console წერს „No data available“, ამიტომ მანამდე ლაბორატორიულ გაზომვას ვეყრდნობით. ამ საიტსაც ჯერ ასეთი მონაცემი არ აქვს — ზემოთ მოცემულ გაზომვაში ამიტომაა მხოლოდ ზომები და რაოდენობები.
