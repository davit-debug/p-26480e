ტექნიკური SEO: ინდექსაცია, სიჩქარე და ხარვეზების გასწორება

ტექნიკური SEO-ს სამუშაოს ცვლილებების რაოდენობით ვზომავთ. თითოეულ ცვლილებას ჟურნალში ვწერთ თარიღით, მიზეზითა და შემოწმების შედეგით. ამ გვერდზე ნახავთ, რას ვამოწმებთ, რა ინსტრუმენტებით და რას მიიღებთ ყოველ თვეს.

რა არის ტექნიკური SEO

ტექნიკური SEO არის სამუშაო საიტის იმ ნაწილზე, რომელსაც ვიზიტორი თითქმის ვერ ხედავს, Googlebot კი ყოველ ვიზიტზე ამოწმებს: რომელ გვერდზე შეუძლია შესვლა, რას პასუხობს სერვერი, რომელია გვერდის მთავარი ვერსია და რამდენად სწრაფად იხსნება ის ტელეფონზე. ტექნიკური შეცდომის გამო კარგი ტექსტიც შეიძლება დაიკარგოს: გვერდი ინდექსში არ ხვდება ან ძიებაში მისი დუბლიკატი ჩანს. ტექნიკური SEO ტექსტსა და ბმულებს არ ცვლის, ის ქმნის პირობას, რომ ორივემ იმუშაოს.

Google საიტს სმარტფონის ბოტით კითხულობს და ინდექსაციასა და პოზიციებს მობილური ვერსიის მიხედვით განსაზღვრავს (Google-ის დოკუმენტაცია, ინგლისურად). ამიტომ ყოველ შემოწმებას მობილური ვერსიით ვიწყებთ.

რას ვამოწმებთ

ინდექსაცია

Search Console-ის „გვერდების ინდექსაციის“ განყოფილებაში ჩანს, რომელი მისამართი რა მიზეზით დარჩა ინდექსის გარეთ. ამ სიას საკვანძო სიტყვების რუკას ვადარებთ: რუკის ყველა გვერდი ინდექსში უნდა იყოს, დანარჩენები კი არა აუცილებლად. ვამოწმებთ robots.txt-ს, noindex-სა და sitemap-ს. sitemap-ში მხოლოდ ის მისამართები უნდა იყოს, რომლებიც 200 კოდს აბრუნებს და ინდექსაციისთვისაა განკუთვნილი.

მისამართები და სერვერის პასუხები

ვამოწმებთ გადამისამართების ჯაჭვებს (A → B → C, როცა საკმარისია A → C), გატეხილ შიდა ბმულებს, 5xx შეცდომებსა და „რბილ 404“-ს, როცა გვერდი ცარიელია ან მასზე „ვერ მოიძებნა“ წერია, სერვერი კი 200 კოდს აბრუნებს. საიტს ერთი ვერსია უნდა ჰქონდეს: https, www-ით ან მის გარეშე. დანარჩენი ვარიანტები 301 გადამისამართებით მთავარ ვერსიაზე უნდა გადადიოდეს.

დუბლიკატები და კანონიკური მისამართი

ერთი და იგივე შინაარსი ხშირად რამდენიმე მისამართზე იხსნება: ფილტრის პარამეტრით, UTM-ნიშნით, დიდი ასოებით ან ბეჭდვის ვერსიით. ვამოწმებთ rel="canonical"-ს და იმას, რომელი მისამართი აირჩია Google-მა (ეს URL-ის შემოწმების ხელსაწყოში ჩანს). Google-ისთვის canonical ძლიერი სიგნალია და არა ბრძანება, ამიტომ შიდა ბმულები და sitemap-იც იმავე მისამართზე უნდა მიუთითებდეს. მრავალენოვან საიტზე hreflang-საც ვამოწმებთ, რომ ენობრივი ვერსიები ერთმანეთზე სწორად მიუთითებდეს. მაღაზიებში დუბლიკატები ყველაზე გავრცელებული პრობლემაა (იხ. ონლაინ მაღაზიის SEO).

საიტის სიჩქარე და Core Web Vitals

Core Web Vitals მობილურისა და კომპიუტერისთვის ცალ-ცალკე ფასდება. თითოეულ მაჩვენებელს თავისი ზღვარი აქვს. შედეგი „კარგია“, თუ ამ ზღვარს გვერდის ჩატვირთვების სულ მცირე 75% აკმაყოფილებს (web.dev, ინგლისურად):

  • LCP (გვერდის მთავარი ელემენტის ჩატვირთვა): კარგია არაუმეტეს 2,5 წამისა;
  • INP (რეაგირება შეხებასა და კლიკზე): კარგია არაუმეტეს 200 მილიწამისა;
  • CLS (განლაგების მოულოდნელი ძვრა გვერდზე ყოფნისას): კარგია არაუმეტეს 0,1-ისა.

ვამოწმებთ სურათების ზომასა და ფორმატს, სხვა სერვერიდან ჩატვირთულ შრიფტებსა და სკრიპტებს, ჩატისა და სხვა ვიჯეტების კოდს, რომელიც ტელეფონზე გვერდის რეაგირებას ანელებს.

JavaScript და რენდერინგი

თუ გვერდის ტექსტი ან ბმულები მხოლოდ JavaScript-ის შესრულების შემდეგ ჩნდება, Google მათ რენდერინგის შემდეგ ხედავს. ეს ცალკე ეტაპია და შეიძლება დაგვიანდეს; თუ სკრიპტი შეცდომით ჩერდება ან დაბლოკილია, ტექსტი საერთოდ არ ჩანს. URL-ის შემოწმების ხელსაწყოში ვადარებთ საწყის HTML-სა და იმას, რასაც Google რენდერინგის შემდეგ ხედავს. ბმული უნდა იყოს ჩვეულებრივი HTML-ბმული (a ელემენტი href-ით): Google, როგორც წესი, მხოლოდ ასეთ ბმულს მიჰყვება.

სტრუქტურირებული მონაცემები

schema.org-ის მონიშვნა მანქანისთვის გასაგები ფორმით აღწერს იმას, რაც გვერდზე უკვე ჩანს: ორგანიზაციის სახელს, ფილიალის მისამართს, პროდუქტის ფასს, სტატიის თარიღს. ვამოწმებთ, ხომ არ შეიცავს მონიშვნა შეცდომებს და ემთხვევა თუ არა გვერდის ხილულ ტექსტს. თუ მონიშვნაში ისეთი შეფასება ან ფასია, რომელიც გვერდზე არ წერია, ეს წესების დარღვევაა. გაფართოებულ შედეგს (ფასს ან შეფასებას ძიებაში) Google თავად ირჩევს: სწორი მონიშვნა ამის წინაპირობაა, მაგრამ შედეგს არ განსაზღვრავს.

ტერმინების (canonical, noindex, hreflang, Core Web Vitals და სხვ.) მოკლე განმარტებები SEO ლექსიკონშია.

ყოველთვიური სამუშაო და ერთეული

ტექნიკური SEO-ს ერთეულია ცვლილება, ანუ ერთი პრობლემის შესწორება ერთ ადგილას: შაბლონში, საიტის პარამეტრებში ან ერთ გვერდზე. შაბლონის ან მთელი საიტის დონეზე შესწორება ერთ ცვლილებად ითვლება, რამდენ გვერდსაც არ უნდა ეხებოდეს (როგორ ითვლება ერთეული). ასეთი ცვლილებებით ვიწყებთ, რადგან ისინი ერთდროულად ბევრ გვერდს ასწორებს. ტარიფში მითითებული რაოდენობა მინიმუმია.

თვის სამუშაო ხუთი ნაწილისგან შედგება:

  1. შემოწმება. საიტს ვამოწმებთ კრაულერით (სკანირების პროგრამით), რომელიც Googlebot-ის მსგავსად ბმულიდან ბმულზე გადადის. შედეგს წინა თვეს ვადარებთ: ახალი 404, ახალი გადამისამართება, გვერდი, რომელსაც title დაეკარგა ან noindex დაემატა. Search Console-ში ვამოწმებთ ინდექსაციის მიზეზებს, Core Web Vitals-ს, სერვერის შეცდომებს, უსაფრთხოებისა და ხელით მიღებული ზომების განყოფილებებს.
  2. რიგი. ჯერ ვასწორებთ იმას, რაც გვერდების ინდექსაციას უშლის ხელს, შემდეგ შაბლონის შეცდომებს, რომლებიც ბევრ გვერდს ეხება, შემდეგ საკვანძო სიტყვების რუკის მნიშვნელოვან გვერდებს და ბოლოს ცალკეულ გვერდებს.
  3. ჩაწერა. ყოველ ცვლილებას ჯერ ცვლილებების ჟურნალში ვწერთ (რა, სად და რატომ) და მხოლოდ ამის შემდეგ ვახორციელებთ.
  4. დანერგვა. თუ საიტის მართვის პანელზე წვდომა გვაქვს, ცვლილებას თავად ვნერგავთ. თუ კოდს თქვენი დეველოპერი მართავს, ვუგზავნით დავალებას: რა შეიცვალოს, რომელ შაბლონში ან ფაილში და როგორ შემოწმდეს. რომელ თვეში ითვლება ასეთი ცვლილება, წერია ტარიფების გვერდზე: როდის ითვლება ერთეული.
  5. გადამოწმება. შეცვლილ მისამართებს ხელახლა ვამოწმებთ კრაულერითა და URL-ის შემოწმების ხელსაწყოს ცოცხალი ტესტით. Search Console-ში შესწორების ვალიდაციას თავად ვიწყებთ, თუ სრული უფლებები გვაქვს. თუ არა, ამას თქვენ გთხოვთ, რადგან შეზღუდული უფლებების მქონე მომხმარებელს ვალიდაციის დაწყება არ შეუძლია. Core Web Vitals-ის შესწორებას Search Console 28 დღის განმავლობაში აკვირდება, ამიტომ შედეგი ხშირად მომდევნო თვის ანგარიშში ჩანს.

რას იღებთ

  • ცვლილებების ჟურნალი, მეთოდის მესამე ეტაპის დოკუმენტი. ყოველ ჩანაწერში მითითებულია თარიღი, მისამართი ან შაბლონი, რა შეიცვალა, რატომ (რომელმა შემოწმებამ აჩვენა), როგორ შემოწმდა და, თუ ცვლილებას დეველოპერი ნერგავს, როდის გაეგზავნა დავალება. თანამშრომლობის ბოლოს ჟურნალს სრულად გადმოგცემთ.
  • ანგარიშის ტექნიკური ნაწილი, ყოველი თვის 30 რიცხვამდე: ინდექსირებული გვერდების რაოდენობა და ინდექსის გარეთ დარჩენილი მისამართები მიზეზების მიხედვით; Core Web Vitals მობილურზე („კარგი“, „გასაუმჯობესებელი“ და „ცუდი“ მისამართები), თუ მონაცემები საკმარისია; თვეში შესრულებული ცვლილებები ტარიფის მინიმუმთან შედარებით და მომდევნო თვის გეგმა. ფორმატს ანგარიშის ნიმუშში ნახავთ.

რას არ ვაკეთებთ

  • ახალ საიტს არ ვაწყობთ და დიზაინს არ ვცვლით: ეს ტარიფში არ შედის. თუ პრობლემის გასასწორებლად საიტის გადაკეთებაა საჭირო, ტექნიკურ მოთხოვნებს ვუმზადებთ იმას, ვინც საიტს აწყობს.
  • PageSpeed-ის ქულისთვის საიტის ფუნქციას თქვენი თანხმობის გარეშე არ ვთიშავთ. თუ ჩატი, ფორმა ან ანალიტიკის სკრიპტი გვერდს ანელებს, გაჩვენებთ გაზომვასა და ვარიანტებს; გადაწყვეტილება თქვენია.
  • Googlebot-სა და ვიზიტორს განსხვავებულ შინაარსს არ ვაჩვენებთ. Google ამას cloaking-ს უწოდებს და სპამის წესებით კრძალავს.
  • Indexing API-ს ჩვეულებრივი გვერდებისთვის არ ვიყენებთ. Google-ის დოკუმენტაციით ის მხოლოდ ვაკანსიებისა და პირდაპირი ვიდეოტრანსლაციების გვერდებისთვისაა.
  • გვერდებს მასობრივად არ ვშლით და noindex-ით არ ვხურავთ სიისა და თქვენი თანხმობის გარეშე.

კითხვები ტექნიკურ SEO-ზე

01უნდა იყოს თუ არა PageSpeed-ის ქულა 100?

არა. 0–100 ქულა ლაბორატორიული გაზომვაა სიმულირებულ ტელეფონზე და გაშვებიდან გაშვებამდე იცვლება. Google-ის დოკუმენტაციის მიხედვით, სრულყოფილ ქულაზე მუშაობა მხოლოდ SEO-ს გამო შეიძლება არ ამართლებდეს დახარჯულ დროს. კარგი Core Web Vitals არც მაღალ პოზიციას ნიშნავს ავტომატურად. ჩვენ ვუყურებთ რეალური ვიზიტორების სამ მაჩვენებელს და ვასწორებთ იმას, რაც „კარგ“ ზღვარს სცდება.

Google: გვერდის გამოცდილება (ინგლისურად)

02რას ნიშნავს Search Console-ის სტატუსი „Discovered – currently not indexed“?

Google-მა მისამართი იცის, მაგრამ გვერდი ჯერ არ ჩამოუტვირთავს. მისივე განმარტებით, სკანირებას ხშირად იმიტომ გადადებს, რომ საიტის სერვერი არ გადაიტვირთოს. ვამოწმებთ, მიდის თუ არა გვერდზე შიდა ბმულები, არის თუ არა ის sitemap-ში და სჭირდება თუ არა მას ინდექსი საერთოდ: ფილტრების კომბინაციებს, მაგალითად, არ სჭირდება. Google ისიც წერს, რომ საიტის ყველა მისამართი ინდექსში არ მოხვდება და ეს ნორმალურია.

Google: გვერდების ინდექსაციის განყოფილება (ინგლისურად)

03რატომ არ აქვს ახალ საიტს Core Web Vitals-ის მონაცემები?

Search Console-იც და PageSpeed Insights-იც რეალური ვიზიტორების მონაცემს Chrome-ის მომხმარებლების ანონიმური გაზომვებიდან (Chrome UX Report) იღებს. სანამ ვიზიტები საკმარისად არ დაგროვდება, Search Console წერს „No data available“, ამიტომ მანამდე ლაბორატორიულ გაზომვას ვეყრდნობით. ამ საიტსაც ჯერ ასეთი მონაცემი არ აქვს, ამიტომ ზემოთ მოცემულ გაზომვაში მხოლოდ ზომები და რაოდენობებია.
